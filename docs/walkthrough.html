XLDR — an interactive walkthrough

Five steps through the file this toolkit was written for: no header row, two kinds of record interleaved, and a column near the front saying which is which. Every value below is computed from the file and the spec as they currently stand — change a control and watch the rows change.

A file that names nothing

five lines, two kinds, no header

Here is the whole input. There is no header row, so no field has a name to be referred to by; fields are addressed by position, counting from one. And it is not one shape: an order line and an order carry different things in different places.

The first component says which kind a line is — O for an order, L for one of its lines. Nothing in the file says that; it is knowledge you bring.

The usual answer to a file like this is a hand-written step that splits it by record type before anything general-purpose is allowed near it. That step is where the format knowledge goes to hide. The next four acts put it in a spec instead.

Which lines are of a kind

discriminator — nth, and equals or matches

A record selector says which lines are its own. In a flat file every line is a candidate, so the question is which to keep, and a discriminator answers it: where to look, and what to look for.

Counting stays absolute within the line, so component 1 is the discriminator itself and a kind's payload starts at 2. A selector with no discriminator keeps every line. And matches matches the value whole — try O.*, then try . and watch both selectors claim everything.

Where a value sits

fieldSelector — nth, counting from one

Each record selector declares the fields it reads. With no header there is nothing to name, so each says which component it takes. Change one and watch the column fill with something else.

A component the line does not have is null, not a failure — one short line should not cost you the other ninety thousand. Point qty at component 5 to see it.

What the text means

type — TEXT, INTEGRAL, DECIMAL, TEMPORAL

A field selector may declare a type, and the shared conversion turns the text into it before it is bound. Declaring none leaves the value as text.

A value that will not convert fails the load and says which record and which field it was — there is no silent null and no partial row.

TEMPORAL rather than DATE: the type has always carried a time of day and binds as a timestamp, so it was renamed at 0.47 and the old name is refused by name rather than ignored.

Where it lands

mapping — two tables, one transaction

The second half of the spec says where the records go. Each record selector is mapped to a table, and each field to a column. The names are independent: ordered in the input half becomes ordered_on in the output half.

Both tables are filled in one transaction. That is the point of one arriving file being one spec rather than two: if either mapping fails the whole file is rolled back, so there is no state in which the orders are loaded and their lines are not.
